The query behind the problem, and why

When CPU, IO or log writes spike, the advisor names the few queries responsible and their share of the load, reads their execution plans, and explains the cause in plain language.

  • Implicit conversions, large scans, key lookups, spills, memory grants
  • Plan regressions with a one-line "force the good plan" fix
  • Missing indexes linked to the queries that need them
  • Who runs the query: user, machine and application

Who ran it, from where NEW

Every running session shows the user, the machine and its IP address, the application, and a status you can act on: Running, Runnable (waiting for CPU), Suspended (with the wait) or Sleeping.

  • Sleeping sessions that hold an open transaction are listed, because they hold locks
  • Filter by status, or type a user, machine, application or text
  • Top queries remember who ran them, after they finish

Where the time went, at any moment

Active sessions are sampled every two seconds and broken down by wait: CPU, IO, locks, log, memory, parallelism. Click any point to see exactly what was running and who was blocking whom.

  • Deployments, schema and setting changes marked on every chart
  • Learned baselines: alerts when something is unusual for that hour

Blocking chains, live and in history NEW

See the whole chain: the head blocker, what it's doing, how long its transaction has been open, and everyone waiting behind it, with each session's user, machine and application.

  • Chains stay whole when the head blocker is connected to another database
  • Every past incident keeps its chain at its worst moment, one click away
  • History as far back as you keep it, with paging and a filter

Deadlocks you can actually fix

Deadlocks are grouped into recurring patterns, drawn as a lock graph, and explained step by step, with prevention advice for the specific pattern.

Index reports with the evidence NEW

Unused indexes with how long usage was counted, duplicates and overlapping indexes with a removal script that includes the rollback, missing indexes, and indexes that cost many writes for every read.

  • Index usage by query: which statements seek, scan, look up or update each index
  • SQL Server, PostgreSQL and MySQL

Parameter sniffing, proven NEW

For each cached plan with parameters, SQL Monitor compares the value it was compiled for with the column's statistics histogram: rows expected for that value, for a typical value and for the heaviest one, plus the real spread of rows and duration per call.

  • Ranked fixes: OPTION (RECOMPILE), OPTIMIZE FOR UNKNOWN, Query Store hints, plan sensitive optimization

What the application is doing to the database NEW

Three reports for problems that start in the application: statements the client gave up on (timeouts) and why, chatty queries that run thousands of times a minute, and connection churn from applications that don't pool connections.

  • Each timeout is labelled: slow statement, blocked, timeout setting, or cancelled
  • Reports run only when you ask, on a short connection that gives way to application locks

A complete inventory in one click NEW

Hardware, edition, version and patch level, configuration with non-defaults flagged, databases, files and volumes, logins and roles, Agent jobs, availability groups and linked servers, plus what needs attention.

  • Every database's compatibility level and the release it behaves like, so old ones stand out

Health checks with the fix attached

Backups against your RPO, Availability Groups and geo-replication, Agent jobs, CHECKDB, capacity forecasts, configuration, security and end-of-support dates. Every problem comes with a script.

Privacy and FAQ

Does any of my data leave my network?

No. There is no telemetry. The only optional connections are an update check that reads the public release list, and AI explanations if you turn them on with your own Anthropic key (literal values are masked). See the privacy statement.

What permissions does it need?

Read-only monitoring permissions: VIEW SERVER STATE / VIEW DATABASE STATE on SQL Server (plus SELECT on a few named msdb tables for backups, jobs and inventory), pg_monitor on PostgreSQL, PROCESS and read access to performance_schema on MySQL. Scripts are included. Two reports have optional extras: a small Extended Events session for client timeouts, and SELECT on the tables whose statistics histograms the parameter sniffing report should read.

How much load does it add?

Light queries every 15 seconds, query statistics every minute, and heavier checks every 10 minutes or less often. Every query has a 30-second timeout, and each feature can be switched off. Reports run only when someone opens them, on their own short connection with a 5-second lock timeout and low deadlock priority, so they always give way to your application.

Can my whole team use one installation?

Yes. Install it on a Windows server and run the included setup script: it puts IIS with HTTPS and your certificate in front, starts SQL Monitor in the background at startup, and turns on sign-in. Each DBA gets their own account and role. Until sign-in is on, SQL Monitor only answers requests from the server itself, so it is never an open console on your network. A Linux / Docker setup is available on request during the beta.

Can I export an inventory for audits or our CMDB?

Yes. The Inventory report downloads as a self-contained HTML report (prints to PDF) or an Excel workbook with one sheet per section, for one database, one server or every server at once. Passwords, password hashes, job step commands and mail content are never read.

Is it free?

Yes, during the beta. Beta testers will be offered a discount if a paid edition follows.

Windows warns about the download. Is it safe?

New downloads from small publishers trigger SmartScreen until they build a reputation. Compare the file's SHA-256 with the .sha256 file on the release page, then choose More info > Run anyway.
